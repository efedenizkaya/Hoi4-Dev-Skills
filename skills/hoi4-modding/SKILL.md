# HOI4 Modding Skill

Expert companion for building, reviewing and debugging Hearts of Iron IV
mods. Grounded in the game's own machine-generated documentation
(`documentation/*.md`, regenerated by the game every patch) and verified
through the game's own error log — not through memory, not through wiki
scrapes.

> **Verified against HOI4 1.19.4.1 ("Operation Postern") on 2026-10-30.**
> The game changes every patch; this stamp goes stale by design. Re-derive
> current data instead of trusting it:
>
> ```bash
> python tools/extract.py        # game docs -> extracted/<version>/*.json
> python tools/validate.py <mod_dir>
> python tools/error_triage.py <log> --against <baseline>
> ```

## Core rules (always apply)

1. **Verify, don't assume.** After writing or changing mod files, run the
   verification loop below. Never claim a mod "works" without evidence.
2. **Check the name against the game, not memory.** Effect/trigger/modifier
   availability changes every patch. When unsure a name exists in the
   user's version, check `extracted/<version>/{effects,triggers,modifiers}.json`
   (create it with `tools/extract.py` if missing) and say so when you could
   not check.
3. **Scope flow is the #1 source of bugs.** Know where you are:
   - `ROOT` = the scope the effect/trigger block was entered from (event
     receiver, focus owner).
   - `FROM` = the scope that initiated the interaction (e.g. the country
     that fired `country_event` on someone else).
   - `THIS` = the current scope after the last scope change.
   - `PREV` = the scope before the last scope change.
   An effect valid in COUNTRY scope silently misbehaves when the block is
   actually in STATE scope. When a doc entry lists supported scopes, honor
   it. CLAIM(scope-flow)
4. **Localisation files are UTF-8 with BOM**, one `l_<language>:` block,
   keys `key:<version>: "text"`. No BOM = the game may not load the file.
   CLAIM(loc-bom)
5. **Tabs vs spaces**: the game accepts both in script files, but vanilla
   uses tabs — match the surrounding file's style when editing existing
   files. Localisation files use spaces. CLAIM(tabs)
6. **Never commit game-derived data** into a mod repo or this one; extract
   it locally.

## Evidence lanes (cheapest lane that answers the request)

| Lane | When | How |
|---|---|---|
| 1. Static lint | any script change | `python tools/validate.py <mod_dir>` — braces/quotes, duplicate IDs, missing loc keys, vanilla overrides |
| 2. Log triage | after a game run, or when given a crash log | `python tools/error_triage.py logs/error.log --against baseline.log` — only deltas matter |
| 3. Game run | when lanes 1–2 are insufficient, or for runtime behavior | user launches with `-debug` (Steam launch options), then lane 2 |

For a one-symptom question read only the matching reference section; do not
preload unrelated references. Lead findings with file/line evidence. If no
defect is established, say so and list the remaining test gaps.

## Verification loop (for every mod change)

1. Baseline: if a recent `error.log` exists, copy it (e.g. `baseline.log`).
2. Apply the change; run lane 1; fix all new errors it reports.
3. Ask the user to launch the game (with `-debug` when possible), then run
   lane 2. Negative deltas = fixed, positive = introduced.
4. Report: what changed, what was verified, what could not be verified.

## Known gaps (honesty)

- Exhaustive effect/trigger semantics beyond what the game's own doc files
  state are NOT embedded here — complex scripted-GUI and variable-lane
  references are planned but not yet written; say so when a task needs them.
- Runtime behavior cannot be tested without the user launching the game;
  never simulate that evidence.
- This skill ships no tools itself; the verification commands live in this
  repository's `tools/` and must be available on PATH (run from repo root).

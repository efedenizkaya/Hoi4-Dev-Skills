# HOI4 Dev Skills — Design Document

Date: 2026-10-30
Status: Draft for approval
Owner: Efe Deniz Kaya

## Intent and Why

An open-source (MIT), multi-agent "Agent Skill" that makes AI coding assistants
(Claude Code, Codex, Cursor, Gemini CLI) write **accurate, current, verified**
Hearts of Iron IV mod code.

The niche is nearly empty. The only comparable project
([eightman999/hoi4-modding-skills](https://github.com/eightman999/hoi4-modding-skills),
MIT, 21 skills) has good bones but: dialogue-style skills that bloat agent
context, no verification workflow, no game-version grounding, and wiki HTML
copied into an MIT repo (license conflict — the HOI4 wiki is CC BY-NC-SA).
The quality playbook exists in [msayib/roblox-dev-skill](https://github.com/msayib/roblox-dev-skill)
(MIT): a single router skill, a claims register, tested examples, version
stamping, honest gap labeling. This project adapts that playbook to HOI4's
unique advantage: **Paradox ships self-documenting debug logs** — running the
game with `-debug` makes the game itself dump its current effects/triggers/
errors into the user's logs folder. Our reference data and our verification
loop are both derived from the user's own game install, per game version.

Success looks like: an AI assistant using this skill creates a focus tree /
event / decision / MIO that passes the game's own error.log with zero new
errors, in the user's game version, on the first or second try.

## Goals

1. **Single router skill** (`hoi4-modding`) per the Agent Skills spec
   (agentskills.io): SKILL.md < 500 lines with core rules + a routing table
   into `references/` (progressive disclosure), multi-agent install scripts.
2. **Engine-derived reference data**: `tools/extract.py` reads the game's
   `-debug` log dumps from the user's own install and produces
   version-stamped JSON databases (effects, triggers, modifiers, scopes,
   event targets). No game data is committed to the repo.
3. **Verification workflow baked into the skill**: (a) static lint via
   `tools/validate.py` (syntax balance, duplicate IDs, missing loc keys,
   file placement), (b) error.log triage workflow ("run game with -debug,
   diff error.log before/after, classify and fix"), (c) optional CWTools
   GitHub Action recipe for CI.
4. **Claims register discipline**: every hard claim (a limit, a behavior,
   "X does not exist") in references is tied to a source — a game dump, a
   game-file inspection, or a wiki page (attributed, CC BY-NC-SA noted,
   paraphrased not copied) — tracked in `docs/claims-register.md`.
5. **Honesty**: game version verified against is stamped in SKILL.md; unverified
   claims are labeled; a re-derive command tells agents/users how to refresh.
6. **Dogfooding**: validated against the owner's real, hand-made mod
   (`mod/germany`) throughout development.

## Non-goals

- Not an MCP server; ships no execution surface beyond local Python scripts.
- Does not redistribute Paradox game files or wiki text.
- No balance/design advice as authority (style guidance yes, "the right
  way to balance" no).
- No mod packaging/upload automation for Steam Workshop (documentation only).

## Anti-goals (failure modes to avoid)

- Dialogue-template skills ("Step 1.1: ask the user...") that bloat context.
- Any game data or wiki copy committed to the repo.
- Claims that cannot be traced to a dump, game file, or attributed source.
- Skills that trigger unreliably (description must carry concrete keywords).

## Approaches Considered

### Reference data pipeline
- **A. Extractor pipeline (CHOSEN)**: user runs `tools/extract.py` against
  their own game install (official `documentation/*.md` files, regenerated
  by the game each version; `-debug` logs as supplement) → version-stamped
  JSON generated locally.
  Clean copyright, self-updating every patch, makes the "verified against
  X" claim real. Cost: one setup step for users.
- B. Commit extracted DBs: zero user setup but distributes Paradox-derived
  data (gray area) and goes stale unless the maintainer re-runs it.
- C. Wiki-based: license conflict (CC BY-NC-SA ↔ MIT) and stale by design.
- Hybrid option adopted: repo additionally commits **sanitized metadata**
  (game version, counts of effects/triggers, diff summaries per release)
  produced by the extractor — versioned, factual, not game content.

### Validation tooling
- **A. Two layers (CHOSEN)**: own stdlib-Python linter for instant, agent-
  callable checks (brace/quote balance, duplicate IDs across files, loc key
  existence, misplaced files, common mistakes like `= {` vs `=`) plus
  documentation of CWTools / cwtools-action for deep CI validation.
- B. CWTools only: deep but .NET-bound, not callable from inside an agent.
- C. Own linter only: full control but cannot match CWTools' rule coverage.

### Skill architecture
- **A. Single router skill (CHOSEN)** over B. skill-per-topic package
  (maintenance + trigger-collision cost) and C. hybrid (middle ground,
  unnecessary while references/ covers the long tail).

## Decided (owner-approved)

- Target: HOI4 1.18.x first; multi-agent via spec compliance + install
  scripts (roblox-dev-skill pattern: one stored copy, links/copies into each
  detected agent dir).
- Single router skill; references carry the depth.
- Approaches A/A as above.
- **Extractor input**: `-debug` dumps first; where a domain has no dump,
  the extractor parses the user's local game install as a fallback
  (CWTools-style). Local use only — nothing game-derived is committed.
- **Reference files are self-sufficient**: they carry stable conceptual
  knowledge (syntax, scope flow, gotchas, worked examples — paraphrased
  and attributed). Exhaustive/up-to-date API lists come from the local
  extractor output; the skill directs agents to run `extract.py` and
  degrades gracefully when it has not been run.
- **Evals are semi-automated**: `validate.py` / `error_triage.py` checks run
  automatically; game-truth verification (error.log diff) is a documented
  manual procedure, applied by the owner during development.
- **Test story, four layers**: (1) pytest for tools, (2) evals harness,
  (3) dogfooding on the owner's real mod, (4) CI (skills-ref validate +
  cwtools-action demo).
- **Platform support tiers** (owner-approved):
  - *Tested and verified*: ZCode (owner's current client) and Claude Code —
    the documented, verified tier.
  - *Best effort, spec-compliant*: Codex, Gemini CLI, OpenCode, Cursor,
    Copilot — the Agent Skills spec + install script targets these, marked
    "untested" honestly in README.
  - Owner is on Windows 10; Unix install paths are shipped but marked
    untested.

## Phases

- **Phase 0 — Discovery ✅ (done 2026-10-30, on this PC)**: game version
  1.19.4.1 confirmed; official `documentation/*.md` corpus inventoried and
  sampled; logs folder structure and error.log format captured from the
  owner's mod context; Workshop content root located. Output feeds the
  extractor input spec (`docs/setup-game-data.md`).
- **Phase 1 — Tools**: `extract.py` (dump → JSON + metadata summary),
  `validate.py` (rule set v1), `error_triage.py`; pytest suite; run all
  against `mod/germany`.
- **Phase 2 — Skill core**: SKILL.md router (core rules: scope flow ROOT/
  FROM/THIS, version stamp, verification loop, routing table) + 4 highest-
  value references first (events, national-focus, debugging-and-logs,
  mod-structure), claims register started.
- **Phase 3 — Breadth**: remaining references, assets/ templates, evals from
  dogfooding the owner's mod.
- **Phase 4 — Release polish**: install scripts for Claude Code/Codex/Cursor/
  Gemini CLI, README (EN, with screenshots), CI (pytest + skills-ref
  validate + cwtools-action demo), CHANGELOG, GitHub topics, publish.
